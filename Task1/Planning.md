## Анализ текущей схемы и проблем продавца

Система состоит из следующих доменов:

### MES 
- UI на React, typescript. Которым пользуются операторы, для изготовления изделий
- Backend сервис на C# 
- БД Postgres 
- Интеграция c CRM через RabbitMQ
- S3 хранилище для 3-Д моделей изделия
### CRM
- CRM UI, через который взаимодействуют сотрудника компании для взаимодействия с покупателем
- CRM API - backend сервер 
- SHOP DB - общая база с доменом магазина
- RabbitMQ - для интеграции с MES
### Shop
- Shop UI - с которым взаимодействуют покупатели изделий 
- Shop API - backend магазина 
- Shop DB - база данных 


### Статусы заказа 

- INITIATED [онлайн-магазин] — пользователь завёл новый заказ или положил товары в пустую корзину.
- FILE_UPLOADED [онлайн-магазин] — пользователь загрузил файл с 3D-моделью или создал его с помощью конструктора.
- SUBMITTED [онлайн-магазин] — пользователь нажал на кнопку «Сделать заказ».
- PRICE_CALCULATED [MES] — система посчитала стоимость заказа.
- MANUFACTURING_APPROVED [CRM] — заказ подтверждён, его можно отдавать в производство.
- MANUFACTURING_STARTED [MES] — оператор взял заказ в работу.
- MANUFACTURING_COMPLETED [MES] — оператор выполнил заказ.
- PACKAGING [MES] — оператор начал упаковывать заказ.
- SHIPPED [MES] — заказ отправлен покупателю.
- CLOSED [CRM] — заказ завершён. Он закрывается после получения сообщения от транспортной компании или вручную.

## Анализ проблем
Из описанных компанией проблем можно выделить следующие, отсортированные в порядке важности:
1. Заказы либо не сохраняются вообще, либо зависают в одном из статусе. Даже если все условия для перехода в новое состояние удовлетворены
2. Долгая прогрузка системы MES. Операторы долго ждут пока страница загрузятся, и к тому же видят не самые актуальные заказы
3. Сыпится слишком много заказов. С открытием API может создаться слишком много заказов за промежуток времени, с которым Александрит не справится физически. А если начнется DDOS атака, то ситуация станет еще хуже
4. Статусы заказа хранятся в разных базах. У заказа есть множество статусов, которые изменяются разными сервисами, и возможо, еще и каждый статус хранится в своей базе. Смена статуса происходит синхронно, из-за чего могут возникать проблемы свойственные синхронному взаимодействию.


## Предлагаемые решения в порядке приоритета

1. Определение SLO и SLA сервисов и сценариев. Предлагается раметить сценарии по критичности, и для критических сценариев, и handler dj установить SLO 99% Uptime. То есть допускается для каждых 100 запросов, не более одной ошибки. Обсудить с бизнесом возможность простановки SLA на смену между статусами. Например, если заказ не перешел из статуса MANUFACTURING_APPROVED в MANUFACTORING_STARTED - то создавать инцидент на саппорт для расследования. 
2. Добавление мониторинга. Для отслеживания состояния системы, наполненности очереди, SLI handler ов сервисов. Мониторинг важнейшая часть системы, без нее по хорошему вообще нельзя выкатываться в прод. Не видим, что происходит с ситемой = не понимаем, функционирует ли она как надо, и функционирует ли вообще
3. Добавление трейсинга. В первую очередь нужно понимать, где запрос застревает, какой сервис дает бОльшее количество ошибок, и какие запросы ухудшает SLI критических сценариев. Без понимания, где запросы "застревают двигаться дальше будет сложно"
4. Кеширование новых заказов. Для ускорения загрузки MES страницы с заказами и увеличения скорости обработки операторами предлагается:
   1. Класть в кеш данные заказов, которые находятся не в терминальных статусах
   2. Сортировать заказы в порядке создания заказов
5. Добавить rate-limiter в MES-API сервис открытый для внешних пользователей, чтобы снизить риски DDOS атак
6. Добавление ELK стека. Для аггрегации логов и поиска по ключевым полям или сообшениям
7. E2E тест прохождения заказа, для проверки решения на release окружении
8. Переход на event-driven взаимодействия. Добавление APACHE Kafka в систему и обмен статусами заказа черз Kafka, а не синхронными взаимодействиями. Почему Apache Kafka, а не RabbitMQ? Главное - RabbitMQ хранит сообщение в виде очереди, сообщение удаляется после первого Acka, если нескольким сервисам понадобится один и тот же event, то необходимо для каждого сервиса создавать отдельную очередь. Apache Kafka более масштабируемая чем RabbitMQ и гораздо дольше хранит сообщения, отправленные в топик. RabbitMQ лучше подходит для задач по доставке команд или задач, Apache Kafka лучше подходит для event Driven взаимодействий, если статусы будут менять несколько сервисов. Так при расширении и добавлении новых микросервисов, каждый из них сможет подписываться на единый топик, в который шлются события изменения статуса о заказе

## Целевая архитектура на полгода

Какой вы видите целевую архитектуру через полгода?

С учетом довольно скромной команды разработки, разработать получится немногое, поэтому выберем топ 3 иницативы

- Полноценный мониторинг с помощью Grafana + (Prometheus | Graphite) на каждом сервисе
- Кеширование информации о новых заказах для ускорения выдачи
- 1 E2E тест, который прогоняется перед релизом в прод, для проверки флоу заказа
- Несколько API тестов, для проверки критичных ручек
- Rate limiter, как минимум на MES API, желательно еще и на Shop API
- Трейсинг запросов и обогащение каждого запроса traceID и spanID
- В идеале развернутый ELK стек, но не топ приоритет 
- Вынос информации, требуемой для CRM домена в отдельную базу. Переход на паттерн Database Per Service

Перейти на event-driven архитектуру с текущей командой, задача довольно амбициозная и не топ приоритетная, поэтому эту задачу можно отложить 

Если выделить топ 3 инициативы, над которыми нужно начинать работу уже сейчас:
1. Развернуть Grafana + Prometheus и добавить откидывание метрик во все приложения в формате Prometheus
2. Интеграция MES с Redis для хранения информации о заказах не в терминальных статусах для ускорения выдачи
3. Трейсинг для отслеживания причины падения запросов => дальнейший фикс проблемных мест и ручное изменение статусов заказов.
